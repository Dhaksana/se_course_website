Lecture 12: Interfaces, Components, and Quality

1. Interface Design

What it means

Interface design describes how the software communicates with systems that interoperate with it, and with humans who use it. An interface implies a flow of information and a specific type of behavior.

Why it matters

A brilliant backend is useless if the user cannot understand the UI, or if other systems cannot securely connect to the API. Interfaces act as literal contracts.

Core Interface Principles in Practice

An interface is a contract. Applying good principles ensures that the developers or users interacting with your contract aren't constantly frustrated.

1. Consistency

The same action should yield the same result. If one API endpoint uses `getUser()`, another shouldn't use `fetchAccount()`. This reduces the cognitive load on the consumer.

// Bad: Inconsistent verbs/nouns
api.getUser();
api.deleteClient();
api.fetchOrder();

// Good: Consistent naming conventions
api.getUser();
api.deleteUser();
api.getOrder();

2. Feedback

Every action must have a clear, observable reaction. A silent failure in an API or a frozen button in a GUI leaves the user guessing if their action succeeded.

// Good: Always return status
public ApiResponse processPayment() {
    if (success) {
        return new ApiResponse(200, "Payment processed");
    }
    return new ApiResponse(400, "Insufficient funds");
}

3. Error Handling

Errors should be forgiving, informative, and prevent the system from crashing. Instead of throwing a raw database exception, translate it into something the caller can understand. 

// Bad: Leaking system internals
throw new SQLException("Table 'users' not found");

// Good: Informative and safe
throw new UserException("Unable to load profile. Please try again later.");

4. User-Centricity

Place the user in control and reduce memory load. Provide sensible defaults so the caller doesn't have to memorize a 10-argument constructor just to create a basic object.

// Good: Reducing memory load
Notification notif = new Notification.Builder()
    .setTo("user@example.com")
    // Subject and Priority have sensible defaults automatically!
    .build();
// The Interface (Contract)
interface PaymentProcessor {
    boolean process(double amount);
}

// The Implementations (Must follow the Contract)
class StripeProcessor implements PaymentProcessor {
    @Override
    public boolean process(double amount) {
        // Stripe specific API logic here
        return true;
    }
}

class PayPalProcessor implements PaymentProcessor {
    @Override
    public boolean process(double amount) {
        // PayPal specific API logic here
        return true;
    }
}
It's not just buttons!
"Interface" in Software Engineering isn't just GUI. If you think it's all about making buttons rounder, wait until you meet an API that requires a 300-page manual just to authenticate!

2. Component-Level Design

What is a Component?

A component is a modular, deployable, and replaceable unit of software. While Architecture Design decides that a "Billing System" should exist, Component-Level Design decides exactly how the Billing System is built internally.

Think of a component as a black box. It exposes a strict public Interface for other parts of the system to use, but severely hides its internal Implementation (the algorithms, data structures, and helper classes it uses to do its job).

Component Design in Practice

Designing a good component relies heavily on two metrics:

  • High Cohesion: The component should do exactly one thing very well. A `BillingComponent` should not also handle sending promotional marketing emails.
  • Low Coupling: The component should not rely on the internal details of other components. It should only interact through defined interfaces.
// --- THE INTERFACE (Public Contract) ---
// This is the ONLY part exposed to the rest of the application.
public interface BillingComponent {
    Receipt chargeCustomer(String customerId, double amount);
}

// --- THE IMPLEMENTATION (Hidden Internals) ---
// These classes are package-private. The rest of the app doesn't know they exist!
class StripeBillingImpl implements BillingComponent {
    private TaxCalculator taxCalc = new TaxCalculator(); // Internal helper

    @Override
    public Receipt chargeCustomer(String customerId, double amount) {
        double total = amount + taxCalc.calculate(amount);
        // Execute complicated internal logic...
        return new Receipt(total, "Paid");
    }
}

// Internal helper class, completely hidden from the outside world.
class TaxCalculator {
    double calculate(double baseAmount) { return baseAmount * 0.08; }
}

Notice how the implementation details (like the `TaxCalculator` and the decision to use Stripe) are completely hidden behind the `BillingComponent` interface. This allows us to replace `StripeBillingImpl` with `PayPalBillingImpl` later without breaking the rest of the app!

Exam Angle: OO vs Traditional Component Design

If asked to compare: OO components focus on collaborating classes containing encapsulated state and behavior. Traditional logic focuses on processing functions and data structures passing sequentially.

OO design focuses on encapsulated objects messaging each other, whereas traditional design focuses on sequential functions passing data structures.

3. Deployment Design

What it means

Deployment design is the absolute final blueprint for where your code runs in the real world. You have designed the logic, but now you must map those software subsystems (components) to physical or virtual hardware (nodes).

Why it matters: The Real-World Constraints

In architectural design, it's easy to assume infinite memory and instantaneous communication. Deployment design forces you to face reality:

  • Bandwidth & Latency: If your Web Server component talks to your Database component inside a `for` loop, and they are deployed on servers thousands of miles apart, the network latency will cripple your application.
  • Scalability vs Hardware: If your software is built as one giant monolith, it requires an equally giant, expensive server to run. By designing smaller components (like microservices), you can map them across dozens of smaller, cheaper deployment nodes.
  • Reliability: If your Login Service is deployed to exactly one physical server node, a simple power outage takes down your application. Good deployment design maps multiple identical components across redundant nodes.

4. Pattern-Based Design

Design patterns are proven, documented solutions to recurring design problems. Just as civil engineers use established patterns to build bridges (suspension vs. truss), software engineers use patterns to build software components.

You don't need to invent a new way to notify users of a state change—the Observer Pattern already solves this beautifully. You don't need to invent a new way to restrict a database connection to a single instance—the Singleton Pattern handles it.

The Three Levels of Patterns

  • Architectural Patterns (High-Level): Structures the entire application. Example: Model-View-Controller (MVC).
  • Design Patterns (Mid-Level): Defines how specific components collaborate. Example: The Observer pattern for event handling, or the Strategy pattern for swappable algorithms.
  • Idioms (Low-Level): Language-specific tricks and best practices. Example: Using Python's list comprehensions instead of manual loops.

5. Design Quality & Evaluation

Evaluating the Design

We evaluate designs through formal technical reviews. A design review is not about finding fault with the designer; it's about finding flaws in the logic, missing requirements, or overly complex implementations before they are committed to code. The attributes of a good design include:

  • Correctness: Does it fulfill the requirements? A design might be elegant, but if it doesn't solve the user's problem, it is incorrect.
  • Completeness: Are all elements modeled? Every feature requested in the requirements document must have a corresponding component or module in the design.
  • Consistency: Do the views agree with each other? For example, if the Logical View shows a `User` class with a `DateOfBirth` attribute, the Data Design must have a corresponding database schema to store that `DateOfBirth`.
  • Traceability: Can every design choice be traced back to a specific requirement? If a component exists in the design but maps to no requirement, it is either "gold-plating" (unnecessary extra work) or a sign of a poorly written requirement document.

Traceability means every design component must link back a specific requirement. If it doesn't, it shouldn't exist!

Common Mistake
Skipping traceable design reviews. If you jump straight to code without verifying the design, congratulations! You just successfully built the completely wrong system, but hey, at least the code compiles!
