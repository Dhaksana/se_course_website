Lecture 10: Foundations of Design Engineering

1. Introduction to Design Engineering

What it means

Software design is the technical kernel of software engineering. It encompasses the set of principles, concepts, and practices that lead to the development of a high-quality system or product. It is the phase where the "what" (requirements) is transformed into the "how" (implementation).

Why it matters

Without design, you are building an unstable system that will fail under minor changes. It is the only way that we can accurately translate a customer's requirements into a finished software product or system. Design impacts quality, project cost, and risk dramatically.

Requirements are the destination; code is the vehicle; Design is the bridge that gets you there. Without the bridge, the vehicle falls into the chasm... and we all know what happens when you drive your code into a chasm (Hint: Stack Overflow!).

How it appears in practice

In practice, design engineering manifests as a "modeling activity". Before typing lines of code, teams draw architectural diagrams (like UML), mock interfaces, define database schemas, and establish component contracts.

Exam Angle: Requirements vs Design

You may be asked to distinguish between analysis/requirements modeling and design modeling. To earn full marks: state that Requirements focus on the problem domain (WHAT the system must do), whereas Design focuses on the solution domain (HOW the system will be built). Use the phrase "technical kernel."

Requirements answer 'what' the system should do. Design answers 'how' the system will accomplish it, serving as the technical kernel of software engineering.
Common Mistake
Students often confuse "design" with just "UI design". While drawing pretty buttons is fun, if the internal architecture is held together with digital duct tape and hope, the app will still crash.

XKCD 1425: This perfectly illustrates why understanding the how (Design) is so critical when presented with the what (Requirements).

2. Design Concepts

A set of fundamental concepts has evolved over the history of software engineering. These form the bedrock of good design.

Abstraction & Refinement

Abstraction allows designers to focus on solving a problem without worrying about low-level details. At the highest level of abstraction, a solution is stated in broad terms using the language of the problem environment. At lower levels, a more detailed description of the solution is provided. For example, "driving a car" is a high-level abstraction, while "depressing the clutch and moving the gear shift" is a lower-level abstraction.

Analogy Time!
Abstraction is like ordering a pizza. You just say "I want a Pepperoni Pizza!" You don't need to instruct the chef on how to knead the dough or preheat the oven.

Refinement is the complementary top-down strategy—starting abstract and slowly elaborating on the details. Refinement causes the designer to elaborate on the original statement, providing more and more detail as each refinement occurs. Abstraction and refinement help the designer deal with complexity.

Modularity & Separation of Concerns

Software is divided into separately named and addressable components (modules) that are integrated to satisfy problem requirements. Separation of Concerns suggests that any complex problem can be more easily handled if it is subdivided into distinct pieces that can each be solved independently. This reduces the overall cognitive load and enables parallel development.

Modularity Rule of Thumb
Don't put all your code in one file. If scrolling through your main class takes longer than reading a Harry Potter book, you desperately need modules! 
public void processUserOrder(int userId, int itemId) {
    // Monolithic function doing everything
    Database db = Database.connect();
    User user = db.query("SELECT * FROM users WHERE id=" + userId);
    Item item = db.query("SELECT * FROM items WHERE id=" + itemId);
    
    if (user.getBalance() >= item.getPrice()) {
        user.setBalance(user.getBalance() - item.getPrice());
        EmailService.send(user.getEmail(), "Order placed!");
    }
}
// Handled in separate, independent modules
public void processUserOrder(int userId, int itemId) {
    User user = userService.getUser(userId);
    Item item = inventoryService.getItem(itemId);
    
    if (paymentService.charge(user, item.getPrice())) {
        emailService.sendReceipt(user.getEmail());
    }
}

Breaking a monolith into smaller, manageable modules reduces complexity and makes maintenance easier.

Information Hiding

The principle of information hiding suggests that modules should be characterized by design decisions that hide from all others. Modules should be specified and designed so that their internal data and algorithms are inaccessible to other modules that have no need for such information. This protects the system from ripple effects during changes because local changes remain isolated.

Functional Independence, Cohesion & Coupling

This is arguably the most critical concept. Functional independence is achieved by developing modules with "single-minded" function and an aversion to excessive interaction with other modules. We measure this through two qualitative criteria: cohesion and coupling. Cohesion is an indication of the relative functional strength of a module. A cohesive module performs a single task, requiring little interaction with other components in other parts of a program. Coupling is an indication of the relative interdependence among modules. Coupling depends on the interface complexity between modules, the point at which entry or reference is made to a module, and what data pass across the interface.

Relationship Advice
High Cohesion means loving what you do and being complete on your own. Low Coupling means not being overly clingy to your partner modules! 
class EmployeeSystem {
    // This class does everything (Low Cohesion) and requires global state (High Coupling)
    private DatabaseConnection globalDbConnection;

    public EmployeeSystem() {
        this.globalDbConnection = DB.connect();
    }
    
    public void calculateTaxesAndPrintPaystub(int id) {
        double salary = this.globalDbConnection.getSalary(id);
        double tax = salary * 0.2;
        System.out.println("Paystub: " + (salary - tax));
    }
}
class TaxCalculator {
    // High Cohesion: only calculates taxes. 
    // Low Coupling: takes raw data instead of needing a DB connection.
    public static double calculateTax(double salary) {
        return salary * 0.2;
    }
}

class PrinterService {
    public static void printPaystub(double netPay) {
        System.out.println("Paystub: " + netPay);
    }
}
Exam Angle: Cohesion vs Coupling

Expect a question asking to define and relate these two. Rule of thumb: We want High Cohesion (a module does one thing well) and Low Coupling (modules are relatively independent of one another). Explain that this makes the system easier to test, maintain, and extend.

High Cohesion means a module performs a single, well-defined task. Low Coupling means modules have minimal dependencies on each other. Both are required for maintainable software.

Refactoring & Design for Quality

Refactoring is the process of changing a software system to improve its internal structure without altering its external behavior. It is how design improves continuously.

3. The Design Model

What it means

The Design Model is the equivalent of an architect's blueprints for a house. It requires multiple views to represent the software from different perspectives.

The Five Design Elements

The translation of the requirements model to the design model results in five distinct elements:

1. Data Design

What it is: Transforms information domain models into database schemas and physical data structures.

Why it matters: Without structured, normalized data, the rest of the application will struggle with fetching and storing information efficiently.

Artifacts: ER Diagrams, Data Dictionaries.

2. Architectural Design

What it is: Defines the relationship between the major structural elements of the software.

Why it matters: It provides the big-picture scaffolding (like MVC or Microservices) that dictates how data flows across the system.

Artifacts: Component Diagrams, Layered Logic Models.

3. Interface Design

What it is: Describes how the software communicates with other systems and humans.

Why it matters: The interface is the ultimate contract. A poorly designed UI frustrates users, and an inconsistent API breaks integrations.

Artifacts: Wireframes, API Specs (OpenAPI/Swagger).

4. Component-Level Design

What it is: Transforms architectural elements into a procedural description of software components.

Why it matters: This is where the actual algorithms, class structures, and encapsulated logic are strictly defined before coding begins.

Artifacts: Class/Activity Diagrams, Pseudocode.

5. Deployment Design

What it is: Indicates how software functionality and subsystems will be allocated within the physical computing environment (hardware nodes).

Why it matters: Dictates the scalability and reliability of the system under real-world constraints like network latency, memory limits, and power redundancy.

Artifacts: UML Deployment Diagrams, Network Topology Maps.

Common Mistake
Forgetting deployment! Many modern developers stop at component design, forgetting that deployment topology affects architectural design directly.
