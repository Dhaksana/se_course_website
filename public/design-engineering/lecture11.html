Lecture 11: Data & Architectural Design

1. Data Design

What it means

Data design translates data objects defined as part of the analysis model into data structures at the software component level and, when necessary, a database architecture at the application level.

Why it matters

Bad data design leads to inefficient algorithms and a fragile database. Creating the right data abstractions is essential before you write functions that manipulate that data.

How it appears in practice

Mapping entity-relationship diagrams (ERDs) or class diagrams created during requirements analysis to relational tables, NoSQL documents, or in-memory arrays and dictionaries. Defining data integrity and constraints.

Memory Loss?
Remember: "persistent data" is the stuff the database remembers after a power outage. "transient data" is the stuff that vanishes faster than your motivation on a Friday afternoon! Both fall under Data Design.
Exam Angle: Analysis vs Design Data

You may be asked how data is mapped. State that Analysis-level Data focuses on real-world entities and relationships, whereas Design-level Data translates these into specific databases formats, keys, indexes, and memory-efficient data structures.

Data design bridges abstract requirements models into concrete database schemas and localized software data structures, ensuring integrity and efficiency.

2. Architectural Design

What it means

Software architecture represents the overarching structure of the software system. It encompasses the components (e.g., databases, middleware, UI), the ways they interact, and the data consumed or produced.

Architectural Views

Because architecture is complex, it cannot be represented by a single diagram. We use multiple views to describe it to different stakeholders:

  • Logical View: Represents the abstractions mapping to requirements (e.g., classes, user entities, and their relationships). This view is primarily for the developers and systems analysts to ensure business requirements are met.
  • Process View: Focuses on the dynamic aspects of the system—concurrency, threads, and execution behavior. It shows how the system handles multiple users and processes simultaneously, which is critical for performance engineers.
  • Development/Code View: Shows how modules and files are physically organized within the development environment (e.g., packages, libraries, namespaces). Useful for programmers managing the codebase.
  • Deployment/Physical View: Describes how the software elements are mapped to physical hardware nodes (servers, devices, cloud containers). This is essential for network and deployment engineers.

The MVC Architecture: The Controller receives input, strictly separating the Model (data) from the View (UI).

Common Architectural Styles

Hover over the cards below to explore different architectural styles.

Layered (N-tier)

UI → Business Logic → Data Access. Clear separation of concerns.

Components are organized in layers. Each layer provides services to the layer above it. Best for traditional line-of-business apps.

Client-Server

Distributed components where one acts as a host and others as requestors.

Clients request info, servers provide it. High scalability, centralizes data.

Pipe-and-Filter

Independent components execute data transformations sequentially.

Data sequentially passes through a series of components (filters). Best for batch processing or transformations.

MVC Pattern

Strict separation of presentation code from business logic.

Separates data (Model), UI (View), and input logic (Controller). Standard for web apps.

// 1. Presentation Layer (UI / Controller)
class UserView {
    public void handleLogin(String username, String password) {
        // Calls the layer directly below it
        AuthLogic.login(username, password);
    }
}

// 2. Business Logic Layer
class AuthLogic {
    public static String login(String username, String password) {
        // Enforces rules, then calls the layer below it
        User user = DataAccess.getUser(username);
        if (user != null && user.getPassword().equals(hash(password))) {
            return "Success";
        }
        return "Failure";
    }
}

// 3. Data Access Layer
class DataAccess {
    public static User getUser(String username) {
        // The ONLY layer allowed to touch the database
        return db.query("SELECT * FROM users WHERE name=?", username);
    }
}
Exam Angle: Justifying Architecture

Exams frequently ask you to choose an architecture for a given scenario. To score well, you MUST mention Trade-offs. E.g., "I choose Client-Server for the banking app because it centralizes security and data consistency, at the cost of requiring a continuous network connection."

Choosing an architecture requires balancing quality attributes. Always justify the choice with explicit trade-offs like scalability vs simplicity, or performance vs maintainability.
